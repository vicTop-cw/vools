先对齐一下“打包成可复用工具”的产品定义，再给演进计划。

我把它理解为：actus 是一个 CLI，能把个人或团队的一组 .actus.md 动作打成一个可分发的「动作包」（action pack），包里携带信任级别、依赖、权限和典型成本声明；另一个人或团队一条命令安装、检查、执行。 不是桌面 App，不是在线市场，不是平台。如果你想的不是这个形态，先纠正我，下面的计划才成立。

产品定义（冻结版）
项	定义
形态	单二进制/单 pip 包的 CLI
核心对象	动作包（.actuspack = tar + manifest.json + 动作文件 + 可选签名）
核心命令	pack / inspect / install / run / ledger
差异点	包内携带治理元数据，inspect 时可见，装之前就能判断“能不能信、大概花多少钱”
不是	动作市场、在线 registry、MCP server、可视化编辑器、工作流引擎、Cloud
这个定义的关键约束是：所有价值必须在“打包—检查—安装—执行”这条链上闭环，不依赖任何在线服务。在线服务是阶段 4 才讨论的事。

阶段 0：冻结范围与格式（第 1 周）
交付物：

docs/actionpack-format.md：manifest 的字段定义。最小集：

pack_id、pack_version、author、created_at

actions[]：每个动作的 id、version、trust、entry、deps、permissions、cost_hint（可选，形如 {"unit": "api_call", "typical": 3}）

source：git remote + commit hash（如果动作库在 git 里）

signature（可选，阶段 3 才实现）

docs/not-doing.md：不做清单，写死，每次想加功能先看它。

.actus.md 最小字段集的最终确认——比现有 schema 草案砍掉 industry、purpose、context_applies、demo、pricing 等非执行必需字段，只留 id/name/version/trust/entry/description/deps/permissions。分类字段以后可以加，但不能阻塞 MVP。

出口条件： 这两份文档写完，自己隔一天再读一遍，确认没有“以后再说”的模糊项。

这一阶段最重要的动作：把“不做清单”写给未来的自己看。独立开发者最大的敌人是中途觉得“顺手加个 X 也不难”。

阶段 1：单人闭环 MVP（第 2—6 周）
目标： 自己用自己的工具管理自己的 5—10 个真实动作。

实现范围：

actus scan / list / validate：解析 .actus.md，校验必填字段和 entry block

actus run <id>：单动作执行，参数走 JSON

actus pack：把当前目录打成 .actuspack

actus inspect <pack>：打印 manifest 摘要、每个动作的 trust/权限/成本声明

actus install <pack>：解包到本地动作库

actus ledger：JSONL 本地账本，记录每次执行的 action_id、started_at、duration_ms、exit_code、cost（动作自己返回的 {"cost": ...} 或从 env 读）

明确不做： MCP server、Quicker 桥接、沙箱、workflow、签名、Cloud、任何 UI。

验证方式： 把自己的日常脚本（至少 5 个，最好是跨 CLI + HTTP 的）迁成 .actus.md，连续 2 周每天用 actus run 跑至少 3 次，每周看一次 actus ledger。

出口条件（全部满足才进阶段 2）：

连续 14 天，每天至少 3 次 actus run，没有一次因为工具本身（不是动作本身）失败而放弃使用

pack → inspect → install 在干净环境（新容器或另一台机器）跑通至少 3 次

ledger 里能看到至少 2 个动作有非零成本记录

如果 6 周后出口条件没满足：砍 ledger，先只做 run + pack + inspect，再给 3 周。如果还不行，这个方向本身可能不成立，进复盘。

阶段 2：团队内闭环（第 7—12 周）
目标： 让一个真实团队（3—5 人）用起来，验证“动作级成本”和“信任随包走”是不是真痛点。

找谁： 你认识的、已经在用 Cursor/Claude Code、已经在写内部脚本、且团队里有一个人愿意当“内部推广者”的团队。不要公开发布等陌生人。

这一阶段要做的产品工作：

修阶段 1 暴露的易用性问题（大概率是路径处理、依赖检查、错误信息）

inspect 的输出要让人看得懂：trust 级别用一句话解释，权限用“这个动作会读写文件/会发网络请求”这种自然语言，不要只打枚举值

ledger 加一个 --by-action 汇总视图，让团队月度回顾时能一眼看到“哪个动作最贵”

明确不做： 签名、跨团队分发、Cloud、按人/按团队的成本聚合（这是 Cloud 的事，先不做）。

验证方式： 团队把他们的内部脚本迁成 .actus.md，用 pack 在团队内分发，连续用 3 周。

出口条件（全部满足才进阶段 3）：

3 周内团队周活跃 ≥ 3 人，周执行次数 ≥ 50

至少发生 1 次“通过 ledger 发现某个动作意外很贵”或“某个动作没人用可以删”

团队主动提出 ≥ 1 个改进需求，且这个需求不是“加个 UI”或“做成平台”（如果是这两类，说明定位没被理解，要重新沟通）

如果阶段 2 失败（团队用了一周就回到原方式，或反馈是“挺好但没必要”）：立即停，不追加功能。 写复盘，判断是“痛点不成立”还是“工具形态不对”。如果是后者，考虑把范围缩到只做 ledger + 成本门禁这一个点，放弃 pack/install。

阶段 3：跨团队复用（第 13—20 周）
目标： 验证“动作包跨团队分发”这件事有人真的需要。

实现范围：

pack 时记录 author + git remote + commit hash（最简来源追溯，不做 GPG）

inspect 增加风险提示：动作声明了 network 或 files:write 权限时给出显式警告；trust: sandbox 但本地无沙箱运行时给出警告

install 支持 --dry-run：只解包和校验，不注册

可选：pack --sign 用本地 GPG key 签名，inspect 显示签名状态（如果时间不够，这个可以砍）

明确不做： 在线 registry、包搜索、评分、下载量统计。分发靠 git 仓库和文件传递。

验证方式： 找第二个团队，让他们 inspect 并 install 第一个团队打的包，跑至少 1 个动作。

出口条件：

≥ 1 次跨团队安装并执行成功

安装方在 inspect 时确实看了 trust/权限信息（访谈确认，不是看日志）

安装方没有在 1 周内卸载

如果阶段 3 失败但阶段 2 通过：把产品定位收窄为“团队内部动作管理工具”，不做跨团队分发。这是一个完全可接受的结局——很多成功的独立工具就停在这里。

阶段 4：决策点（第 21—24 周）
不做新功能，只做判断：

阶段 2	阶段 3	决策
通过	通过	考虑 Cloud（跨组织成本聚合、审计留存），但先做 3 个月付费意向验证，不写代码
通过	失败	定位为团队内部工具，持续维护，考虑一次性买断或赞助模式
失败	—	停，写复盘。可选转向：只做“动作级成本门禁”单点工具
付费意向验证怎么做：不写代码，先跟 3—5 个用过阶段 2/3 的团队聊“如果有一个托管版，能跨团队看成本、留存审计，你们愿意按什么价格付”。如果没人愿意付，Cloud 不做。

贯穿全程的不做清单
写在 docs/not-doing.md 里，每次想加功能先看：

不做动作市场 / 在线 registry / 评分 / 下载量

不做 MCP server（别人的 MCP server 是供给源，不是你的活）

不做 Quicker 桥接（Quicker Connector 已存在）

不自建沙箱（路由到 E2B / CubeSandbox 即可，甚至阶段 1—3 直接不实现 sandbox trust）

不做可视化编辑器

不做 workflow DAG（阶段 1—3 只做单动作 + 简单顺序编排）

不做 Cloud / 多租户 / SSO

不做 LLM 调用封装（动作自己调，Actus 不碰模型）

不做分类体系（industry/purpose 等字段，MVP 不实现）

止损规则
三条，写下来贴在显示器上：
